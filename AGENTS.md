# Publishing Argo findings

This directory is the `gh-pages` worktree of `gigioneggiando/argo`, separate from `BugBounty/Argo` (`main`) and `BugBounty/Fleece` (private registry). The site is published at both `https://gigioneggiando.github.io/argo/` and, via a separate personal-site repository and deployment, `https://gigioneggiando.com/argo/`. Follow both paths for a public finding update.

## 1. Establish what can be public

1. Read `../AGENTS.md`, the relevant `.codex/claude-memory/*-target-status.md`, and the matching Fleece record. Fleece is the private operational source; imported memory is historical. Check the actual upstream PR, issue, advisory, release or commit again at publication time.
2. A new row needs an already public, independently accessible upstream URL. A private GHSA draft or triage URL, unpublished vendor email, Fleece file, local PoC, or predicted CVE is not publication evidence. Verify an advisory is actually published; published does not imply fixed. Respect the vendor's disclosure policy and any embargo. Do not publish vulnerability detail from private material merely because a PR or issue exists: use only what the public upstream record discloses.
3. Verify the finding's public attribution and outcome precisely. `merged` means the linked PR merged; `open` means a public PR is still open; `fixed` needs an identifiable upstream fix even if Luigi's PR closed; `advisory` needs a published advisory and an accurate fixed/unpatched label; `issue` is a public issue. A closed-without-merge PR is not a merged fix. Do not count one vulnerability twice merely because it has GHSA, CVE and Go-vuln aliases. A separate backport may legitimately be a separate public record; state that clearly.
4. If this followed a vendor reply or Fleece status change, update the Fleece finding and relevant target-status note before the site, without copying private evidence to this public worktree. Public-site updates are due when a record becomes public or an existing public outcome changes, not on every private triage step.

## 2. Edit the public source, not the generated pages

- The only authoritative archive source is `content/disclosures.html`. Add or revise a `<section class="case">` and its `.row` records there. Keep a real public project URL, project language, `data-stars` snapshot, short factual blurb, `data-sev`, status class/label, and upstream evidence link(s). Existing anchor rows and multi-link `div` rows are both supported; copy the closest existing pattern. Escape HTML text and attributes. Describe the scope of a fix narrowly enough to match the linked code.
- `index.html` and `findings.html` are generated by `node build.mjs`; never edit those or headline totals by hand. The builder derives counts from source rows: project sections, unique primary PR URLs, advisory rows, resolved rows and unique CVE IDs. These are record counts, not distinct vulnerability or benchmark counts. Reconcile the changed counts with the source and the public upstream state.
- Use the upstream's actual severity for the row. GitHub's `Moderate` is grouped with `Medium` in charts and filters by `build.mjs` and `script.js`; do not create a separate Moderate filter or double-count it. Preserve `Info` if the upstream record uses it. Keep status and severity colours meaningful.
- If a change affects the tool's README claims or a Fleece record, update those separately in their own repositories. `Argo/main` may be PR-only and can contain unrelated local edits; do not overwrite its worktree. Do not add private registry data or scanned target source to this public branch.

## 3. Build, validate, and publish GitHub Pages

1. In `BugBounty/Argo-ghpages`, confirm `git status -sb`, branch `gh-pages`, and the intended diff. Run `node build.mjs` (Node 22+).
2. Check that source, generated `index.html` and `findings.html` contain the expected public URL/title/status exactly once per intended record, and that chart totals equal the source row count. Check links in a browser without authenticated GitHub state.
3. Run `node verify.mjs`, `node verify-controls-stars.mjs`, and `node verify-sorting.mjs` when their browser dependency is available. These scripts currently contain snapshot-specific expectations (e.g. 95 rows/26 projects and a local `.taste-skill/baseline-dom.json`); update those expected counts and inspect any baseline diff for an intentional new/changed record. Do not weaken or blindly regenerate an evidence-preservation check just to make it pass. If the browser tool is unavailable, run the build and source/output checks and report that limit.
4. Commit only the intended public-site files and `git push origin gh-pages` normally; never force-push for routine updates. Verify the GitHub Pages build completed for the pushed SHA, then check the live `https://gigioneggiando.github.io/argo/` and `.../findings.html` (including no-JS/source HTML if relevant). A successful push alone is not a live-site check.

## 4. Verify the automatic personal-site sync

- The personal site's `Build site` workflow checks public `gh-pages` every hour (minute 23 UTC; GitHub can delay schedules), and imports it on every site `main` push or manual run. No manual copy is required for ordinary finding updates. For an immediate refresh, run `gh workflow run build.yml --repo gigioneggiando/gigioneggiando-site --ref main -f only_if_changed=true` after the public commit is pushed.
- The importer reads one exact committed tree: two generated HTML pages, four CSS/JS files and `assets/`. It does not run Argo build scripts or copy notes, Fleece, PoCs or working-tree changes. Build and commit the generated public output here before pushing. The personal-site builder preserves its homepage backlinks and canonical URLs; the existing checks must pass before atomic deployment.
- Verify the personal-site action succeeded and fetch `https://gigioneggiando.com/argo/assets/source.json` with a fresh query string. Its `commit` must match the intended pushed `gh-pages` SHA and `uncommittedSource` must be false. Also check both live Argo pages for the intended public record. A successful Pages build alone does not confirm the personal-site sync. If the scheduled run is delayed, dispatch it manually; investigate a failed run rather than bypassing its checks.
- `public/argo/` in the personal-site repository remains an offline fallback, not a continuously committed mirror. To refresh that fallback explicitly, use the standalone repository's `npm run sync:argo`, then `npm test`, `npm run build` and `npm run check`. The older `source-of-me/personal_website/source/sync-argo.mjs` is a historical preview helper, not the production workflow.
- Keep the repository boundaries and state in the final report: Fleece record, Argo `gh-pages` SHA and Pages result, personal-site SHA and production result. If one surface could not be published, say which one remains stale.
