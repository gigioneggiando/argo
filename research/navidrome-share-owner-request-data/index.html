A share owner is not request data

Navidrome let a logged-in user assign a new share to someone with broader library access by submitting that user's ID. On affected multi-library installations, the share could expose tracks its creator was not allowed to read or stream.

What went wrong

Navidrome lets users create public links for music they want to share. Each share has an owner. That owner is not simply a name shown in the interface: Navidrome uses the owner's library permissions when it resolves the share's contents and serves its tracks.

The native POST /api/share endpoint decoded a userId from the request body into the share model. The repository supplied the logged-in user's ID only when that field was empty. If the client sent a non-empty ID, Navidrome preserved it and stored the share as belonging to that user instead.

That made a server-side authority attribute behave like ordinary request data. In Navidrome 0.63.x, a logged-in user could take a public playlist, submit the ID of another user with access to more libraries, and create a share resolved under that wider access context. The request did not merely choose what to share; it also chose whose permissions would govern the result.

Why it mattered

The advisory rates the issue High with a CVSS 3.1 score of 7.1. On versions 0.63.0 through 0.63.2, any authenticated user could use the affected native API to read and stream tracks from libraries they had not been granted, provided the installation used per-user library restrictions and the attacker could start from a public playlist. The created share also appeared under the other user's name.

The limits are important. The cross-library disclosure requires a meaningful difference between the two users' library access. Before version 0.63.0, spoofing the owner caused mis-attribution but did not create this same cross-library path. The Subsonic createShare endpoint was not affected because it does not accept a userId parameter.

Sharing is enabled by default from 0.63.0. Earlier installations were exposed to the ownership problem only when EnableSharing was enabled. The supplied owner also had to be a real user ID, although a public playlist exposed its owner's ID through the native API.

How it was fixed

Navidrome 0.64.0 makes the ownership rule explicit: a share is always owned by the authenticated user who creates it. The service layer replaces any submitted UserID with the caller's ID before resolving the share, and the persistence layer enforces the same rule again before saving it.

The second check is useful defence in depth. It protects the invariant even if another caller reaches the repository without passing through the usual service wrapper. Regression tests now submit one user's ID while authenticated as another and verify that the stored owner is still the authenticated caller.

This changes behaviour for administrators too: they can no longer create a share on behalf of another user by supplying userId. For installations that cannot upgrade immediately, the advisory's workaround is to disable sharing with EnableSharing = false.

After the patch

Ownership fields often look harmless because they are represented as ordinary IDs. But when an ID determines whose permissions, tenant or library scope a later operation will use, it is part of the authorization model. The server should derive it from the authenticated principal, not accept it as a client preference.

A useful review question is: which fields describe the requested object, and which fields decide the authority under which that object will later be interpreted? Create paths deserve particular attention. Code that fills an owner only when it is missing may appear to provide a safe default while quietly allowing the caller to override the security boundary.
